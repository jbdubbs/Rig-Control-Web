# Dev Notes — RigControl Web

## Current State
A full-stack web + Electron application (Express + Vite + Socket.io) for controlling amateur radio equipment via Hamlib's `rigctld`, with a real-time dashboard (frequency/mode/meters), bidirectional Opus audio, WebCodecs H.264 video, POTA/SOTA/WWFF spots, a CW keyer and GGMorse decoder, Hamlib UDP and FT-710 (FT4222 USB-SPI) spectrum scopes, solar/propagation data, JWT-based authentication, a user-configurable panel grid layout, radio power on/off control (`set_powerstat`) with auto-reconnect, and a WSJTX rig-control/audio bridge for remote digital-mode operation.

## Deferred / Future Work
- [ ] **Dual spectrum scope support (IC-7610, IC-7850/7851):** Both radios expose two independent scopes (Main + Sub) via Hamlib's `spectra[]` array. RigControl Web currently reads only `spectra[0]` (Main). Full support would require: a scope selector UI in the Spectrum Scope panel settings (Main / Sub), either a second `spectrum-data` event channel or an added `scopeId` field in the payload, and potentially a second `SpectrumHamlibPanel` instance for simultaneous display. Deferred until there is user demand or a contributor with one of these radios to test against.
- [ ] **FTDX10/FTDX101 spectrum scope via SCU-LAN10 Ethernet:** The FTDX101MP, FTDX101D, and FTDX10 stream spectrum data through Yaesu's SCU-LAN10 Ethernet accessory using a proprietary UDP protocol. Supporting these radios would require reverse-engineering or documenting the SCU-LAN10 Ethernet frame format (frames are similar to the FT-710 SPI frames per ratmandu/YaesuWFTesting, but delivered over UDP rather than USB SPI) and adding a new server module. The physical SCU-LAN10 device ($~200 USD) would be required at the radio end. Deferred pending hardware access and protocol documentation.

## Decisions Log
| Decision | Rationale | Date |
|----------|-----------|------|
| FT4222 restart wired to `probePowerCapability()`, not just the poll loop's off→on branch | `onPowerOn()` only fired from `pollRig`'s off→on transition, which requires an unbroken TCP session across the power cycle. When the reconnect happened via the auto-reconnect path instead (e.g. a `set_powerstat 1` confirmation timeout destroying the socket, then a fresh connect once the radio finished booting), the poll loop never saw an off→on edge, leaving the FT-710 FT4222 scope reader dead until the user manually toggled the spectrum source. Fixed by also calling `onPowerOn(ctx)` from `probePowerCapability()`, which runs on every connect/reconnect regardless of path. | 2026-07-01 |
| Rig auto-reconnect only on unexpected drops | Retrying every 5 s applies solely to sockets that close unexpectedly (e.g. USB re-enumeration during a power cycle, transient serial errors) — a user-initiated disconnect does not trigger it. A power-on confirmation timeout is treated as an expected, non-error condition (the radio may still be booting) rather than surfaced to the user, since the auto-reconnect loop will pick the connection back up once the radio finishes booting. Timestamped (`HH:MM:SS.mmm`) rig log lines were added specifically so reconnect timing is visible without needing `--debug-rig`. | 2026-07-01 |
| Power-on confirmation via polling, not optimistic state | The first pass optimistically set `powerState = 'on'` as soon as `set_powerstat 1` was sent, before the radio had actually finished booting — controls would unlock while the rig was still unresponsive. Replaced with a `get_powerstat` poll every 500 ms for up to 10 s; the UI shows an amber spinner during this window and only unlocks controls once the radio confirms. | 2026-06-30 |
| `get_powerstat`/`set_powerstat` are the correct command names (not `j`/`J`) | Two earlier fixes were needed to land on the right commands. First pass used `j`/`J` believing lowercase/uppercase followed Hamlib's general get/set convention — but `j`/`J` are actually `get_rit`/`set_rit` in Hamlib's extended protocol, not power control; sending `J ?` as a "get" was interpreted as an invalid `set_rit` call, and the resulting RPRT error caused `probePowerCapability()` to hide the power button for all radios, including the FT-710 which fully supports power control. Corrected to the actual extended-protocol command names, `get_powerstat`/`set_powerstat`, at all three poll sites and both set commands. | 2026-06-30 |
| Single-click power off (no double-click confirm) | The initial power-off implementation required a double-click (button turns amber for 3 s) to guard against accidental power-down. Removed in favor of a single click once the power-on confirmation spinner and clearer "Radio powered down" banner made the power state unambiguous enough that an accidental toggle is easy to reverse. | 2026-06-30 |
| WSJTX bridge audio auto-setup: trigger on `bridgeConnected`, not toggle click | Auto-setup fires when the WebSocket to the bridge helper actually connects (`bridgeConnected` → `true`), not when the user flips the toggle. This ensures virtual audio devices exist (the bridge creates them before starting its WebSocket server). Device detection is platform-aware: Linux uses `/RCW-WSJTX-RX/i` and `/RCW-WSJTX-TX/i` regex on `enumerateDevices()` labels (PipeWire devices created by the bridge). Windows falls back to detecting VB-Audio virtual cable products by label regex — supports VB-CABLE (`/VB-Audio Virtual Cable/i`), Hi-Fi CABLE (`/VB-Audio Hi-Fi Cable/i`), and Cable A–D (`/VB-Audio Cable [A-D]/i`). Windows requires two distinct cables for bidirectional audio; the first detected (by priority order: VB-CABLE > Hi-Fi > A > B > C > D) is assigned as RX (browser → WSJTX output), the second as TX (WSJTX → browser input). If only one cable is found, a specific warning prompts for a second. If none are found, a platform-specific warning guides installation. Previous input device and outbound mute state are stashed in a ref + localStorage for restoration on disconnect. Auto-join audio was attempted but blocked by browser autoplay policy (`AudioContext` requires user gesture) and `server/audio.ts` `startAudio()` unconditionally calling `stopAudio()` first (emits `audio-status: "stopped"`, tearing down the local pipeline); deferred as a known issue. | 2026-06-24 |
| WSJTX bridge PTT: `Number(args) > 0` | WSJTX sends Hamlib PTT type values: 0=OFF, 1=RIG_PTT_RIG_MICDATA, 2=RIG_PTT_SERIAL_DTR, 3=RIG_PTT_RIG (CAT). The previously deployed bundle used strict equality (`args === 1 \|\| args === true`) which only matched type 1 and boolean `true`; type 3 (the default for "Hamlib NET rigctl" connections) evaluated as `false`, silently sending PTT OFF instead of ON. Fixed to `Number(args) > 0` which correctly treats any non-zero value as TX. | 2026-06-24 |
| WSJTX bridge architecture: browser as middleman | The bridge helper cannot connect directly to the RCW server's Socket.io because it's a C binary with no Socket.io client. Instead it runs a raw WebSocket server; the browser's `useWsjtxBridge` hook bridges commands between the helper's WebSocket and the server's Socket.io. ## Architecture Notes
- **Radio Power Control**: For radios supporting Hamlib's `get_powerstat`/`set_powerstat`, `probePowerCapability()` in `server/rigComm.ts` probes once per connect and sets `powerSupported` in the `rig-connected` payload. The Power button lives in `ControlsPanel`'s header (`ControlsPanelHeaderAction`). Power-off (`set_powerstat 0`) tears down PTT, the CW key, the queued-command backlog, backend audio, and spectrum data, then suspends the normal 2 s poll loop for a `get_powerstat` probe every 5 s. Power-on (`set_powerstat 1`) polls `get_powerstat` every 500 ms for up to 10 s before confirming; the frontend shows a spinner during this window via `poweringOn`. `effectivelyConnected = connected && status.powerState !== 'off'` gates all rig controls and drives a "Radio powered down" banner. `onPowerOn(ctx)` restarts backend audio (2 s delay) and the FT4222 scope reader, and fires both from the poll loop's off→on edge and from `probePowerCapability()` on every reconnect, so a power-on reached via auto-reconnect still restarts the scope reader.
- **Rig Auto-Reconnect**: An unexpected TCP socket close (not a user-initiated disconnect) schedules a reconnect attempt every 5 s in `server/rigComm.ts` until the connection succeeds. `server/vlog.ts` rig log lines are timestamped `HH:MM:SS.mmm` so reconnect timing is visible in the rigctld log view; `DEBUG_*` flags can be set via environment variables in addition to CLI flags. A power-on confirmation timeout is treated as expected (radio still booting), not a user-facing error, since the auto-reconnect loop will recover once the radio is ready.
- **WSJTX Bridge**: `wsjtx-bridge.c` (v0.2.0) is a standalone C binary that bridges WSJTX to RigControl Web. Command flow: WSJTX → TCP (rigctld protocol, port 4540) → bridge → WebSocket (JSON, port 4541) → browser `useWsjtxBridge` hook → Socket.io → server `rigComm.ts` handlers → rigctld → radio. The bridge maintains cached rig state updated by `rig-status` WebSocket messages from the browser; GET commands respond from cache (zero latency to WSJTX), SET commands are forwarded and delivered asynchronously via a pending-command queue. `dump_state` returns protocol v1 with `ptt_type=0x1` so Hamlib's netrigctl backend enables PTT. A 3-second cache guard after SET commands prevents stale poll values from overwriting optimistic cache updates. On Linux, the bridge auto-creates PipeWire mono virtual audio devices (`pw-loopback`) named `RCW-WSJTX-RX` and `RCW-WSJTX-TX` for WSJTX audio routing. When the bridge WebSocket connects, `App.tsx` auto-detects virtual audio devices via `navigator.mediaDevices.enumerateDevices()`. On Linux, it matches PipeWire device labels (`RCW-WSJTX-RX`/`RCW-WSJTX-TX`). On Windows, it falls back to detecting VB-Audio virtual cable products (VB-CABLE, Hi-Fi CABLE, Cable A–D) by label regex; two distinct cables are required for bidirectional audio — the first detected is assigned as RX (browser → WSJTX), the second as TX (WSJTX → browser). Auto-switches the WSJTX Audio Output and Local Input (Mic) to the detected virtual devices (stashing original settings for restore on disconnect), and auto-unmutes the mic once the audio pipeline is ready. If insufficient virtual devices are detected, a platform-specific warning is shown and manual configuration is required. The user must still manually "Join Audio" before auto-setup takes effect. Diagnostic logging (`--verbose`) includes ms-precision timestamps, per-command round-trip timing, and PTT-specific tracing. The bridge is currently launched manually by the user; server-managed lifecycle is planned.
- **Authentication**: `server/auth.ts` implements JWT issuance/verification (`jsonwebtoken`), bcrypt password hashing (`bcryptjs`, cost 12), per-IP and per-callsign in-memory rate limiters, and an append-only audit log (`audit.json`, capped at 1000 entries). `registerAuthHandlers` is called on every socket connection and handles `auth:login`, `auth:logout`, and `auth:change-password`. `registerAdminHandlers` handles all `admin:*` events and is gated by `requireAdmin`. Functional Socket.io handlers (rig control, audio, video, etc.) are registered only after JWT validation via `onAuthenticated` callback. Data files (`users.json`, `auth.json`, `audit.json`) are written with mode `0o600`. Default admin account (`ADMIN`/`admin`, `mustChangePassword: true`) is seeded on first launch if no `users.json` exists.
- **Auth Client**: `useAuth` hook (`src/hooks/useAuth.ts`) manages `AuthState` — `"unknown"` (initial, waiting for server response), `"unauthenticated"` (login required), `"must-change-password"` (login succeeded but forced change pending), `"authenticated"` (fully active). On reconnect, state resets to `"unknown"` until the stored token is re-validated. `LoginScreen.tsx` and `ChangePasswordModal.tsx` are pure presentational components; all socket events are handled in `useAuth`. The `nsKey(callsign, key)` helper namespaces `localStorage` keys per user; `clearUserPreferences` and `checkAndClearPreferences` manage remote-triggered preference wipes.
- **Admin Panel**: `AdminTab.tsx` (`src/modals/`) is the admin-only UI. It issues `admin:*` socket requests and renders five sections: Users, Active Sessions, Audit Log, Lockouts, System Info, plus a destructive Factory Reset action guarded by typed confirmation. Mounted only when `role === "admin"` in `SettingsModal.tsx`. `broadcastUsersList` in `server/auth.ts` pushes updated user lists to all currently connected admin sockets after every mutation.
- **Modular Backend**: `server.ts` is a 269-line orchestrator that wires together 11 focused modules under `server/`: `context.ts` defines the shared `ServerContext` object (passed by reference to every module), `tls.ts` handles cert generation, `settings.ts` manages persistence, `rigctld.ts` spawns/monitors the child process, `rigComm.ts` owns the TCP socket and rig polling, `audio.ts` manages naudiodon I/O, `cw.ts` implements the iambic state machine, `video.ts` handles WebCodecs relay, `spectrum.ts` handles Hamlib UDP multicast spectrum data, `yaesuScope.ts` spawns `ft4222-scope-reader` and relays FT-710 SPI spectrum frames, and `vlog.ts` provides six per-subsystem debug helpers (`vlogRig`, `vlogAudio`, `vlogVideo`, `vlogCw`, `vlogInfra`, `vlogSpectrum`) gated by the corresponding `--debug-*` CLI flag (`--debug-spectrum` for the spectrum helper).
- **Modular Frontend**: App.tsx (987 lines, 2 useState calls) is a thin composition root. Business logic lives in 7 custom hooks under `src/hooks/`: `useRigControl`, `useAudio`, `useVideoStream`, `useCWKeyer`, `usePotaSpots`, `useRigctld`, `useCwDecoder`, `useLayoutState`, `usePanelState`. UI structure lives in `src/layouts/` (CompactLayout, PhoneLayout, PhoneStickyBar) and `src/modals/` (SettingsModal, VideoSettingsModal, AudioSettingsModal, SpotSettingsModal, ComboSpotSettingsModal). All layout and modal components are wrapped in `React.memo`; all handlers use `useCallback`.
- **Panel Component System**: Each functional UI section lives in its own file under `src/panels/`. `PanelChrome` (`src/components/PanelChrome.tsx`) provides a consistent collapsible/expandable wrapper with title and optional header-action slots; the `hideCollapse` prop suppresses the chevron for panels with no expandable body (e.g. `AudioFeedPanel`). Current panels: VfoPanel, ControlsPanel, SMeterPanel, AlcPanel, SwrPanel, TabbedMeterPanel, RfLevelsPanel, ModeBwPanel, VideoFeedPanel, AudioFeedPanel, SpotsPanel, SpotComboPanel, CwDecodePanel, CommandConsolePanel, MufMapPanel, SolarPanel, SpectrumHamlibPanel, SpectrumAudioPanel. Layout files import and compose panels.
- **Server-as-Manager**: The Express server is not just a proxy but a process manager for `rigctld`.
- **Event-Driven**: All radio state changes flow through Socket.io to ensure low latency.
- **Graceful Shutdown**: The server listens for `SIGINT`/`SIGTERM` to kill the `rigctld` child process, preventing orphaned processes.
- **Log Buffering**: The server keeps the last 100 lines of `rigctld` output in memory to provide context to newly connected clients.
- **Split VFO State**: Managed as a boolean in the rig status, triggering specific UI color overrides.
- **Multi-Window Awareness**: The backend now avoids resetting the rig connection if a new client connects to the same host/port, ensuring stability across multiple tabs.
- **WebCodecs Video Pipeline**: The Electron app is always the video source. It captures via `getUserMedia` + `MediaStreamTrackProcessor`, encodes H.264 (AVCC, avc1.42001F) with `VideoEncoder`, and emits chunks to the server. The server buffers the latest keyframe (with its AVCC description) and relays all chunks to remote clients, which decode with `VideoDecoder` and render to a `<canvas>`. Any client can configure video settings and request start/stop; the server broadcasts changes to the Electron source.
- **Client Audio Routing**: Uses `getUserMedia` with specific `deviceId` for input and `setSinkId` for output, allowing full control over local audio hardware.
- **Native Audio Backend**: Uses `naudiodon` for direct access to host audio devices (ALSA/Pulse/CoreAudio/WASAPI) without spawning external processes, improving reliability and latency.
- **Multi-Client Mic Policy**: Server tracks `activeAudioClientId` based on client interaction events, enforcing a single-source audio stream to the backend.
- **Low-Latency Audio Pipeline**: Uses 48kHz mono Opus encoding via `libopus-node` and WebCodecs, with `AudioWorklet` for capture/playback and a PCM ring buffer for precise frame slicing.
- **POTA Spots Pipeline**: Browser polls `https://api.pota.app/spot/` on a client-side `setInterval`. Raw results are deduplicated by activator callsign (latest `spotTime` wins), filtered by max age (UTC-corrected by appending `'Z'` to bare ISO strings), mode, and band before being passed to a `useMemo`-derived sorted list. `POTA_BANDS` defines 14 amateur bands as kHz min/max ranges. Settings (`enabled`, `pollRate`, `maxAge`, `modeFilter`, `bandFilter`) are persisted to `settings.json` via the existing `save-settings` socket event.
- **SOTA Spots Pipeline**: Fully functional. Browser polls `https://api2.sota.org.uk/api/spots/-1/all` on a client-side `setInterval`. Results are filtered by max age, mode, and band. `SOTA_BANDS` mirrors the same kHz min/max structure as `POTA_BANDS`. Click-to-tune and SSB USB/LSB resolution work identically to POTA. Settings persisted to `settings.json` alongside POTA settings.
- **WWFF Spots Pipeline**: Browser polls the wwff.world API on a client-side `setInterval`. `WwffSpot` type uses `frequency_khz` (number) and `spot_time` (Unix timestamp). Filtered by max age, mode, and band. Click-to-tune resolves SSB to USB/LSB by 10 MHz boundary. Settings persisted under `wwffSettings` in `settings.json`.
- **All Spots Combo Panel**: `SpotComboPanel` (`src/panels/SpotComboPanel.tsx`) is a thin tab shell that accepts render-prop functions for each spot type's table. `ComboSpotSettingsModal` (`src/modals/ComboSpotSettingsModal.tsx`) provides unified per-type settings in a single tabbed modal. Active tab persisted to `localStorage` under `spots-combo-tab`.
- **MUF Map Panel**: `MufMapPanel` (`src/panels/MufMapPanel.tsx`) embeds SVG propagation maps from prop.kc2g.com. Metric (MUFD/foF2) and time-slot (now/−1h/−12h/−24h) are toggled in a controls bar. Zoom uses `width/height = scale * 100%` on the image wrapper for crisp SVG rendering at any zoom level; clamping keeps the image covering the container. Mouse wheel, drag, and pinch-to-zoom are all supported. Panel height is configured at add-time via the PanelPicker and stored in `GridItem.heightPx`.
- **PanelPicker Config Step**: `PanelPicker` uses a two-step flow for panels with configurable options (`PANEL_CONFIG_OPTIONS` in `layout.ts`). Step 1 lists available panels; step 2 shows per-panel options (height slider, full-width toggle). `GridLayoutCallbacks.addPanel` now accepts an optional `PanelAddConfig`; `useLayoutConfig` maps `fullWidth: true` to `w: 9999` so the compact-layout segment renderer treats the panel as a full-width row.
- **General Settings Modal Tabs**: The settings modal uses a tab bar rendered between the header and content area. `activeSettingsTab` state drives which panel is visible. Adding new tabs requires only adding a string literal to the tab array and a corresponding conditional content block.
- **CW Keyer Pipeline**: Client sends `cw-paddle { dit, dah, straight, t }` events (where `t` is ms since socket connect, computed via `performance.now() - cwConnectTimeRef`). Server-side iambic state machine (`iambic-a`, `iambic-b`, `straight`) reconstructs element timing from these offsets, drives a DTR/RTS serial line via the `cw-key-helper` C binary subprocess, and also handles `rigctld-ptt` keying mode. The C binary is spawned by `openKeyerPort()` in `server/cw.ts` and communicates via stdin (`0`/`1`) / stdout (`OPEN_OK`/`OPEN_ERROR`). A 5 s stuck-key watchdog fires `emitCwKey(false)` if no key-up event arrives. Client-side sidetone uses a separate Web Audio `AudioContext` (oscillator → gain → destination) for zero-latency local feedback; it is initialized in `initSidetone()` only after `localAudioReady` is true, routed to the selected output device via `setSinkId`, and explicitly resumed. `teardownSidetone()` closes and nulls the context whenever the keyer is disabled or `localAudioReady` goes false, ensuring a clean rebuild on the next enable.
- **Phone CW Paddles**: When `cwSettings.enabled` is true and the rig is in a CW mode (`CW`, `CWR`, `CW-R`), the phone sticky bar swaps the PTT button for side-by-side dit (·) and dah (—) touch buttons. Both use `onPointerDown`/`onPointerUp`/`onPointerCancel` with `setPointerCapture` for reliable touch tracking. They set `ditPressedRef`/`dahPressedRef` and call `emitCwPaddle`, and the existing iambic tick loop drives `sidetoneOn`/`sidetoneOff` in response.
- **App Icons**: Platform-specific icons in `assets/icons/` — `rcw.ico` (Windows), `rcw.icns` (macOS), `rcw_512x512.png` (Linux). Bundled in the asar via the electron-builder `files` array. `BrowserWindow` receives the 512px PNG as its `icon` for Linux runtime taskbar display. `app.setName('RigControl Web')` is called before `whenReady()` to set a clean, predictable `WM_CLASS`.
- **Linux Desktop Integration**: `--install` / `--uninstall` CLI flags allow GNOME integration without AppImageLauncher. The install handler reads the icon from `$APPDIR/resources/app.asar`, writes a `.desktop` file with correct `StartupWMClass`, and refreshes icon/desktop caches. Both handlers call `process.exit()` before `app.whenReady()` — no window or GUI is created.
- **Local Speaker Volume**: A `GainNode` (`inboundGainRef`) sits between the `playback-processor` AudioWorkletNode and `AudioContext.destination`. The UI slider (0–200%) drives `gain.value` in real time. Above 100% adds amplification beyond the system volume level; below 100% attenuates. Value persisted in `localStorage` under `local-audio-inbound-volume`.
- **CW Decoder Pipeline**: `GGMorseDecoder` (wrapping GGMorse WASM) runs entirely in the browser. After WebCodecs decodes each Opus packet to F32 PCM, the raw float array is also passed to `cwDecoderRef.current.processSamples()`. This happens unconditionally when `cwDecodeEnabledRef` is true — the mute flag only gates speaker playback, not the decoder feed. WASM is loaded lazily (once) on first toggle; `reset()` is called on disable to flush internal state without unloading the module. Decoded characters append to `cwDecodedText` (capped at 2000 chars), auto-scrolled to the bottom. `cwStats` carries pitch (Hz) and speed (WPM) from the last decoded burst, displayed in a small inline readout next to the text area. The decoder display appears inline in compact/desktop layouts and as a collapsible section in the phone layout.

Three warning states: no cables detected (Windows-specific message pointing to vb-audio.com), one cable detected (prompts for a second), Linux with no PipeWire devices (prompts to run wsjtx-bridge-linux). Recommended free Windows setup: VB-CABLE + Hi-Fi CABLE (both donationware from vb-audio.com). Alternative: VB-CABLE A+B (~5 EUR donation).

> Two real bugs surfaced while building this, both caught before doing damage. (1) The first Playwright config had `reuseExistingServer: true` and no dedicated port — on this dev machine a real instance of the app was already running on port 3000 with a real radio attached over serial (`rigctld -m 1049 ... -r /dev/serial/by-id/usb-Silicon_Labs_CP2105...`), and the e2e run's login flow fired one bad-password attempt against callsign "ADMIN" on that live instance before the mistake was caught (harmless — well under the 10-attempt lockout threshold — but the wrong thing to have happened at all). (2) `playwright.config.ts` is loaded multiple times per run (main process + each worker process); an early version did the scratch-data-dir wipe at module scope, which re-ran mid-suite in a worker process and deleted the live test server's just-seeded `users.json` out from under it, breaking login for whichever spec ran next. Fixed by moving the one-time wipe into a separate pre-script (`tests/e2e/reset-test-data.mjs`), run once via the `test:e2e`/`test:hardware` npm scripts before Playwright itself starts. Also discovered mid-suite that running the 3 spec files across multiple Playwright workers let two tests fight over the single shared rig connection the one shared server process owns — fixed with `workers: 1` in both configs.
